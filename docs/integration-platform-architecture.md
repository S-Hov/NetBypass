# Платформа интеграций NetBypass

Статус: целевая архитектура дальнейшего развития.

Этот документ определяет продуктовые границы NetBypass, устройство платформы
интеграций и обязательные правила для подключения сторонних движков, патчеров,
системных настроек и официальных загрузчиков.

## 1. Назначение продукта

NetBypass развивается как централизованный Windows-инструмент, который собирает
разрозненные способы устранения сетевых и региональных ограничений в одном
понятном интерфейсе.

Пользователь выбирает сервис или приложение, а NetBypass:

1. показывает доступный способ решения;
2. проверяет совместимость;
3. скачивает зафиксированную версию необходимого компонента;
4. применяет заранее подготовленную конфигурацию;
5. проверяет результат;
6. умеет вернуть систему в исходное состояние.

Главная ценность проекта — не самостоятельная разработка всех способов обхода,
а их безопасная, воспроизводимая и удобная интеграция.

```text
NetBypass = каталог решений
          + единый пользовательский интерфейс
          + управление жизненным циклом
          + проверка результата
          + гарантированный откат
```

## 2. Границы собственной разработки

### 2.1. Встроенные возможности NetBypass

Команда NetBypass самостоятельно разрабатывает и поддерживает только небольшой
набор базовых механизмов:

- управление собственным блоком системного `hosts`;
- профили доменов и адресов;
- диагностику DNS, TCP, TLS, HTTP и других необходимых протоколов;
- выбор проверенного адреса;
- безопасное резервное копирование и восстановление;
- в перспективе — встроенный DNS-движок с выборочным DoH/DoT;
- платформу обнаружения, запуска, проверки и удаления интеграций.

`hosts`-движок должен быть доведён до стабильного законченного состояния. После
этого его метод работы принципиально не расширяется: увеличивается каталог
сервисов, актуализируются адреса и проверки, но сам механизм остаётся прежним.

DNS-движок является максимально допустимым расширением собственного сетевого
слоя. Он должен решать ограничения `hosts`: wildcard-домены, CNAME, TTL,
динамические адреса, выборочный защищённый DNS и восстановление настроек
сетевых адаптеров.

### 2.2. То, что не разрабатывается внутри Core

NetBypass не создаёт собственные реализации:

- Anti-DPI;
- перехвата пакетов;
- драйверов Windows;
- сложных алгоритмов десинхронизации DPI;
- патчеров конкретных сторонних приложений;
- средств изменения чужих бинарных форматов;
- универсального proxy или VPN.

Для этих задач используются существующие open-source-проекты. NetBypass
отвечает за их интеграцию, но не выдаёт их функциональность за собственную.

## 3. Основной принцип: всё внешнее является интеграцией

GoodbyeDPI, zapret2, будущие Anti-DPI-движки, патчеры приложений, изменение
региональных параметров Windows и официальные загрузчики должны подключаться
через одну платформу интеграций.

Центральные проекты не должны знать особенности конкретного инструмента:

- `NetBypass.App` не знает аргументы `winws2.exe`;
- `NetBypass.Core` не знает имена служб GoodbyeDPI;
- общий экран не знает, какой файл изменяет конкретный патчер;
- кнопка «Восстановить» всегда вызывает один контракт, даже если одна
  интеграция восстанавливает реестр, а другая — конфигурационный файл.

Добавление новой типовой интеграции не должно требовать изменения
`MainViewModel`, общей навигации, карточек интерфейса или координатора.

## 4. Категории интеграций

Каждая интеграция относится к одной основной категории.

| Категория | Назначение | Примеры |
| --- | --- | --- |
| `network-engine` | Управление внешним сетевым движком | zapret2, GoodbyeDPI, ByeDPI |
| `app-patcher` | Применение исправления к приложению | региональный патчер конкретной программы |
| `system-tweak` | Обратимое изменение Windows | домашний регион Windows |
| `download-tool` | Получение официального дистрибутива | WinGet или официальный vendor CDN |
| `diagnostic-tool` | Дополнительная диагностика | внешний blockcheck-подобный инструмент |

Категория влияет на расположение в интерфейсе и набор ожидаемых возможностей,
но не меняет общий жизненный цикл.

## 5. Уровни интеграции

Платформа поддерживает два уровня. Сначала всегда следует пытаться использовать
декларативный уровень.

### 5.1. Декларативная интеграция

Интеграция состоит из манифеста и рецептов стандартных действий. Собственный
исполняемый код интеграции отсутствует.

Подходит для большинства задач:

- скачать архив или исполняемый файл;
- проверить SHA-256 и Authenticode;
- безопасно распаковать;
- запустить проверенный CLI с фиксированными аргументами;
- изменить разрешённое значение реестра;
- изменить JSON, INI или XML;
- создать резервную копию файла;
- запустить или остановить принадлежащий интеграции процесс;
- проверить процесс, файл, реестр или сетевой endpoint;
- вернуть сохранённое исходное состояние.

Преимущество этого уровня: новую интеграцию можно добавить отдельной папкой с
данными, не компилируя и не изменяя основное приложение.

### 5.2. Кодовый адаптер

Используется только когда стандартных действий недостаточно: нужен сложный
подбор стратегии, нестандартный протокол, собственный формат конфигурации или
особая проверка состояния.

Кодовый адаптер поставляется как отдельная подписанная .NET-сборка и реализует
публичный контракт платформы. Он не добавляется непосредственно в
`MainViewModel` или `NetBypass.Core`.

GoodbyeDPI и zapret2 должны стать первыми эталонными кодовыми адаптерами.

### 5.3. Граница доверия и изоляция

Загрузка DLL через `AssemblyLoadContext` решает конфликты зависимостей и
выгрузку, но не является sandbox. Код, загруженный внутрь процесса NetBypass с
правами администратора, получает те же права, что и приложение.

Целевая процессная модель:

```text
NetBypass.App                 обычные права пользователя
        ↓ descriptors/state
Integration Host             отдельный ограниченный процесс
        ↓ validated plan
NetBypass Elevated Broker    повышение только на время мутации
        ↓ typed operations
Windows resources
```

- UI не должен постоянно работать от администратора;
- Integration Host загружает доверенный кодовый адаптер и строит план;
- Elevated Broker повторно проверяет подпись пакета, разрешения и каждый шаг;
- broker выполняет только известные типизированные операции;
- адаптер не передаёт broker произвольную командную строку или shell-скрипт;
- сетевой движок запускается повышенно только если это действительно требуется;
- обмен выполняется через версионированный локальный IPC с идентификатором
  операции и защитой от подключения чужого процесса.

Во время миграции первые адаптеры могут временно работать внутри существующего
повышенного процесса. Однако удалённый каталог кодовых адаптеров нельзя считать
готовым, пока граница привилегий не реализована.

```text
NetBypass.sln

│   │   ├── Hosts Engine
│   │   ├── DNS Engine
│   │   ├── Diagnostics
│   │   └── Service Profiles
│   │
│   ├── NetBypass.Integration.Abstractions/
│   │   ├── contracts
│   │   ├── states and results
│   │   ├── descriptors
│   │   └── versioned API
│   │
│   └── NetBypass.Integration.Runtime/
│       ├── discovery and validation
│       ├── package installation

    ├── NetBypass.Integration.ContractTests/
    └── integration-specific tests
```

### Ответственность проектов

`NetBypass.Core` содержит только собственные механизмы NetBypass и ничего не
знает о сторонних GitHub-проектах.

`NetBypass.Integration.Abstractions` — маленькая стабильная сборка без UI,
сетевых загрузчиков и платформенной реализации. На неё ссылаются кодовые
адаптеры.

`NetBypass.Integration.Runtime` обнаруживает пакеты, валидирует их, строит план,
выполняет стандартные действия, ведёт журнал и загружает доверенные адаптеры.

`NetBypass.App` строит UI из дескрипторов интеграций и вызывает только общий
координатор.

## 7. Структура пакета интеграции

Идея «одна интеграция — одна папка» является правильной, если папка имеет
строгий формат и проходит проверку до загрузки.

Исходное представление:

```text
integrations/<integration-id>/
├── integration.json             обязательный манифест
├── recipes/                     декларативные операции
│   ├── install.json
│   ├── apply.json
│   ├── verify.json
│   ├── revert.json
│   └── uninstall.json
├── adapter/                     только для сложной интеграции
│   ├── NetBypass.Integration.<Name>.dll
│   └── dependencies/
├── assets/                      только собственные статические данные
├── licenses/                    лицензии и notices upstream
├── schemas/                     дополнительные схемы настроек
├── checksums.json               хеши файлов пакета
├── package.sig                  подпись манифеста и списка хешей
└── tests/                       фикстуры и сценарии интеграции
```

Публикуемое представление версионируется:

```text
%LOCALAPPDATA%\NetBypass\Integrations\<integration-id>\
├── current.json
└── versions\
    ├── 1.2.0\
    └── 1.3.0\
```

Версии устанавливаются side-by-side. Новая версия становится текущей только
после проверки манифеста, подписи, файлов и совместимости. Предыдущая версия
может использоваться для отката.

Папка интеграции не является произвольным набором скриптов. Runtime не должен
автоматически исполнять найденные `.cmd`, `.bat`, `.ps1` или `.js`.

Простейшая декларативная интеграция может состоять фактически из одного
`integration.json`: короткие recipes разрешается описывать inline. Отдельные
файлы используются, когда операция становится большой или переиспользуется.
Таким образом сохраняется сценарий «добавить одну папку и не менять центральный
код», но границы пакета остаются одинаковыми для простых и сложных компонентов.

По умолчанию пакет содержит только метаданные, рецепты и адаптер NetBypass.
Бинарники upstream скачиваются отдельно с официального фиксированного release.
Включать сторонний бинарник непосредственно в пакет можно только когда лицензия
разрешает распространение и это решение явно зафиксировано в аудите.

## 8. Манифест `integration.json`

Манифест описывает интеграцию для каталога, runtime и универсального UI.

Минимальный пример:

```json
{
  "schemaVersion": 1,
  "id": "goodbyedpi",
  "version": "1.0.0",
  "apiVersion": 1,
  "type": "network-engine",
  "display": {
    "name": "GoodbyeDPI",
    "summary": "Anti-DPI движок для выбранных сервисов.",
    "icon": "assets/icon.png",
    "categories": ["Сеть"],
    "tags": ["anti-dpi", "youtube", "discord"]
  },
  "upstream": {
    "name": "GoodbyeDPI",
    "repository": "https://github.com/ValdikSS/GoodbyeDPI",
    "license": "Apache-2.0",
    "version": "0.2.2"
  },
  "implementation": {
    "mode": "adapter",
    "assembly": "adapter/NetBypass.Integration.GoodbyeDpi.dll",
    "entryPoint": "NetBypass.Integrations.GoodbyeDpiAdapter"
  },
  "capabilities": [
    "install",
    "apply",
    "verify",
    "revert",
    "repair",
    "uninstall"
  ],
  "targets": [
    { "kind": "service", "id": "youtube" },
    { "kind": "service", "id": "discord" }
  ],
  "compatibility": {
    "operatingSystems": ["windows-10", "windows-11"],
    "architectures": ["x64"],
    "requiresAdministrator": true
  },
  "permissions": [
    "network-download",
    "process-control",
    "driver-control",
    "write-user-data"
  ],
  "settingsSchema": "schemas/settings.json",
  "recipes": {},
  "security": {
    "checksums": "checksums.json",
    "signature": "package.sig",
    "signingKeyId": "netbypass-catalog-2026"
  }
}
```

Для декларативной интеграции `implementation.mode` имеет значение `recipe`, а
поле `recipes` содержит пути к стандартным операциям.

### Обязательные свойства манифеста

- `id` — глобально уникальный стабильный идентификатор;
- `version` — версия самой интеграции NetBypass;
- `apiVersion` — версия контракта платформы;
- `type` — категория интеграции;
- `display` — данные универсального UI;
- `upstream` — авторство, репозиторий, лицензия и версия стороннего проекта;
- `implementation` — декларативный рецепт или кодовый адаптер;
- `capabilities` — доступные стандартные операции;
- `targets` — сервисы, приложения или системные функции;
- `compatibility` — ограничения ОС, архитектуры и версий приложений;
- `permissions` — заранее объявленные системные воздействия;
- `security` — подпись и хеши пакета.

Неизвестная версия схемы, неизвестное разрешение или неизвестный тип действия
делают пакет несовместимым. Runtime не пытается угадать его поведение.

`checksums.json` перечисляет каждый файл пакета, кроме `package.sig`.
`package.sig` подписывает каноническое представление `integration.json` и
`checksums.json`. После проверки подписи runtime сверяет хеш каждого файла и
только затем читает recipes или загружает assembly.

## 9. Универсальный контракт жизненного цикла

Для кодовых адаптеров используется общий контракт:

```csharp
public interface IIntegrationAdapter
{
    IntegrationDescriptor Descriptor { get; }

    Task<CompatibilityResult> CheckCompatibilityAsync(
        IntegrationContext context,
        CancellationToken cancellationToken);

    Task<IntegrationStateSnapshot> InspectAsync(
        IntegrationContext context,
        CancellationToken cancellationToken);

    Task<IntegrationPlan> PlanAsync(
        IntegrationOperation operation,
        IntegrationRequest request,
        CancellationToken cancellationToken);

    Task<IntegrationOperationResult> ExecuteAsync(
        IntegrationPlan plan,
        IProgress<IntegrationProgress> progress,
        CancellationToken cancellationToken);

    Task<VerificationResult> VerifyAsync(
        IntegrationRequest request,
        CancellationToken cancellationToken);

    Task<RecoveryResult> RecoverAsync(
        IntegrationRecoveryContext context,
        CancellationToken cancellationToken);
}
```

`PlanAsync` и `ExecuteAsync` используются для всех стандартных операций:

```csharp
public enum IntegrationOperation
{
    Install,
    Apply,
    Verify,
    Revert,
    Repair,
    Update,
    Uninstall
}
```

Это предпочтительнее интерфейса с десятками обязательных методов. Одна
интеграция может поддерживать все операции, другая — только `Apply`, `Verify`
и `Revert`. Поддержка определяется `capabilities`.

### Точная семантика операций

- `Install` — получает и устанавливает необходимые файлы, но не включает
  системный эффект;
- `Apply` — применяет патч, настройку или запускает выбранный движок;
- `Verify` — проверяет не наличие файлов, а фактический результат;
- `Revert` — выключает эффект и восстанавливает зафиксированное исходное
  состояние пользователя;
- `Repair` — восстанавливает ожидаемое активное или отключённое состояние;
- `Update` — устанавливает новую версию side-by-side и умеет откатиться;
- `Uninstall` — сначала выполняет `Revert`, затем удаляет принадлежащие
  интеграции файлы;
- `Recover` — завершает или откатывает прерванную транзакцию после сбоя.

Операции должны быть идемпотентными. Повторный `Apply` не создаёт дубликаты,
повторный `Revert` не повреждает уже восстановленную систему, повторный
`Uninstall` возвращает успешное состояние «уже удалено».

## 10. Декларативные действия

`NetBypass.Integration.Runtime` предоставляет ограниченный набор типизированных
действий. Новые типы добавляются только в платформу после отдельного аудита.

Базовый набор:

- `download` — скачать файл только с разрешённого HTTPS-источника;
- `verify-hash` — проверить SHA-256;
- `verify-authenticode` — проверить подпись и ожидаемого издателя;
- `extract-archive` — безопасная распаковка без path traversal и reparse point;
- `copy-file` и `delete-owned-file`;
- `backup-file` и `restore-file`;
- `patch-json`, `patch-ini`, `patch-xml`;
- `set-registry-value` и `restore-registry-value`;
- `start-owned-process` и `stop-owned-process`;
- `create-owned-service` и `delete-owned-service`;
- `create-owned-task` и `delete-owned-task`;
- `run-verified-cli` — запуск только проверенного executable без shell;
- `http-check`, `tcp-check`, `tls-check`, `file-check`, `registry-check`;
- `open-official-url` — действие без системной мутации.

Каждое мутирующее действие обязано:

1. получить текущее состояние;
2. проверить precondition;
3. записать undo-информацию в журнал;
4. выполнить изменение;
5. проверить postcondition;
6. сообщить результат координатору.

Запрещено передавать пользовательский ввод в командную строку без
типизированной валидации. Запрещено запускать команды через `cmd.exe /c` или
PowerShell только ради удобства рецепта.

## 11. Состояния интеграции

Сохранённый флаг не считается источником истины. Состояние определяется через
`InspectAsync` и фактические ресурсы.

```text
NotInstalled
  → Installed
  → Applying
  → ActiveUnverified
  → ActiveVerified

ActiveVerified
  → Reverting
  → Installed

Installed
  → Uninstalling
  → NotInstalled

Любое промежуточное состояние
  → FaultedRecoverable
  → Recovering
  → Installed | ActiveVerified | NeedsAttention
```

Дополнительные состояния:

- `Incompatible` — платформа, версия приложения или политика не подходят;
- `UpdateAvailable` — доступна проверенная новая версия пакета;
- `ExternallyModified` — принадлежащий интеграции ресурс изменён извне;
- `NeedsAttention` — автоматический откат не может быть доказан.

## 12. Координатор интеграций

`IntegrationCoordinator` является единственной точкой запуска операций.

Он отвечает за:

- глобальную блокировку параллельных системных изменений;
- совместимость интеграций;
- конфликты ресурсов;
- построение плана;
- показ плана пользователю;
- write-ahead journal;
- выполнение шагов;
- проверку результата;
- автоматический rollback;
- восстановление после аварийного завершения;
- публикацию прогресса в UI.

Адаптер не должен самостоятельно переключать другую интеграцию. Например,
zapret2 не останавливает GoodbyeDPI напрямую. Он объявляет конфликтующий ресурс
`network-filter:windivert`, а координатор решает, можно ли выполнить безопасное
переключение.

### Модель ресурсов и конфликтов

Интеграция заранее объявляет ресурсы:

```text
hosts:block:netbypass
dns:adapter:<adapter-guid>
process:<canonical-executable-path>
service:<service-name>
driver:<driver-service-name>
registry:<hive>\<path>\<value>
file:<canonical-path>
scheduled-task:<task-name>
network-filter:windivert
```

Координатор запрещает одновременный запуск интеграций с эксклюзивным ресурсом,
если они явно не объявлены совместимыми.

## 13. Resource Journal и восстановление

Журнал является общей инфраструктурой для движков, patch-рецептов, региона,
DNS и будущих интеграций.

Он хранит:

- идентификатор операции и интеграции;
- версию интеграции и upstream-компонента;
- выбранное действие;
- состояние до начала;
- уже выполненные шаги;
- исходные значения файлов и реестра;
- канонические пути и хеши;
- созданные процессы, службы, драйверы и задачи;
- ожидаемое конечное состояние;
- время и результат последней проверки.

Запись выполняется до каждой мутации и атомарно заменяется после неё.

У интеграции нет права удалять ресурс только по совпадению имени. Принадлежность
подтверждается журналом, каноническим путём, хешем, владельцем процесса или
зафиксированным baseline.

При старте NetBypass сначала обрабатывает незавершённые операции, и только затем
показывает обычное управление интеграциями.

## 14. Обнаружение интеграций

`IntegrationDiscoveryService` сканирует только известные корневые каталоги:

```text
<application>\Integrations
%LOCALAPPDATA%\NetBypass\Integrations
```

Алгоритм:

1. найти `integration.json` только на ожидаемой глубине;
2. проверить размер и корректность JSON;
3. проверить версию схемы и API;
4. канонизировать все пути;
5. проверить подпись пакета и `checksums.json`;
6. проверить уникальность `id`;
7. определить совместимую текущую версию;
8. создать `IntegrationDescriptor`;
9. зарегистрировать декларативный рецепт или доверенный адаптер;
10. передать дескриптор универсальному UI.

Неизвестная, повреждённая или неподписанная интеграция не загружается. Она
показывается в диагностике как отклонённый пакет с конкретной причиной.

Каталог не должен загружать каждую DLL, найденную внутри папки. Сборка и точка
входа берутся только из проверенного манифеста.

## 15. Универсальный пользовательский интерфейс

UI полностью строится из `IntegrationDescriptor`, `IntegrationStateSnapshot`,
`capabilities` и схемы настроек.

Стандартная карточка показывает:

- название и иконку;
- назначение;
- поддерживаемые сервисы или приложения;
- текущий статус;
- установленную и доступную версии;
- автора и ссылку на upstream;
- лицензию;
- требуемые права;
- предупреждения;
- стандартные действия, поддерживаемые интеграцией.

Кнопки создаются по возможностям:

```text
install   → Скачать / Установить
apply     → Применить / Включить
verify    → Проверить
revert    → Вернуть исходное состояние
repair    → Исправить
update    → Обновить
uninstall → Удалить
```

### Дополнительные настройки

Интеграция может объявить `settingsSchema` с ограниченными типами полей:

- `boolean`;
- `enum`;
- ограниченное `integer`;
- валидируемая строка;
- выбор сервиса;
- выбор установленного приложения;
- read-only информационный блок.

На первом этапе не поддерживается произвольный XAML от интеграции. Это
сохраняет единый дизайн и исключает выполнение UI-кода неизвестного пакета.

Интеграция также может вернуть дополнительные типизированные действия через
`IntegrationActionDescriptor`, но их отображает стандартный renderer NetBypass.

## 16. Каталог сервисов и связь с интеграциями

Сервис и способ его разблокировки являются разными сущностями.

```text
Service: YouTube
├── Hosts profile: optional
├── zapret2 integration
├── GoodbyeDPI integration
└── future DNS profile
```

```text
Application: Example App
├── region requirement
├── supported patcher integration
└── official download integration
```

Карточка сервиса получает список решений из `targets` всех загруженных
интеграций. Поэтому добавление новой интеграции автоматически добавляет новый
вариант на страницу сервиса без изменения UI-кода.

Если доступно несколько решений, `SolutionResolver` сортирует их:

1. встроенный безопасный метод;
2. уже установленная проверенная интеграция;
3. низкорисковая интеграция без постоянного процесса;
4. внешний сетевой движок;
5. экспериментальный вариант.

Автоматическое применение допускается только для заранее разрешённых
low-risk-вариантов. Остальные требуют явного подтверждения.

## 17. Удалённый curated-каталог

NetBypass не должен превращать результаты поиска GitHub в автоматическую
установку. Сначала репозиторий проходит ручной аудит, затем для него создаётся
и подписывается пакет интеграции.

Каталог содержит:

- список интеграций и версий;
- URL пакета;
- SHA-256;
- подпись;
- канал стабильности;
- поддерживаемые версии NetBypass;
- дату последнего аудита;
- статус upstream-проекта;
- сведения об отзыве небезопасной версии.

Рекомендуемые каналы:

- `stable` — проверенные интеграции;
- `preview` — новые интеграции для тестирования;
- `local-development` — явно включаемый режим разработчика.

Подпись каталога проверяется встроенным публичным ключом. Компрометация GitHub-
репозитория upstream не должна автоматически обновить установленный компонент.

## 18. Работа со сторонними GitHub-проектами

Для каждого кандидата проводится аудит:

1. назначение и реальная необходимость;
2. лицензия и право распространения;
3. наличие исходного кода;
4. история и активность проекта;
5. наличие воспроизводимых Releases;
6. состав бинарников и зависимостей;
7. требуемые права;
8. системные изменения;
9. наличие CLI или silent-режима;
10. возможность проверки результата;
11. возможность полного отката;
12. реакция Windows Defender;
13. ограничения по версиям приложения;
14. отсутствие функций обхода лицензии, DRM и оплаты.

NetBypass скачивает фиксированный release или commit, а не изменяемый `latest`
или ветку `master`. Архив и критические файлы проверяются по хешам. В интерфейсе
всегда показываются настоящее имя проекта, автор, версия, лицензия и ссылка на
репозиторий.

## 19. Политика безопасности интеграций

### Разрешённая область

- сетевые ограничения и DPI;
- DNS-блокировки;
- клиентские региональные настройки;
- официально доступные endpoint и параметры запуска;
- обратимые изменения конфигурационных файлов;
- получение официальных дистрибутивов;
- восстановление функций, отключённых региональной конфигурацией клиента.

### Исключённая область

- обход платной лицензии;
- удаление DRM;
- эмуляция подписки;
- вмешательство в платежи;
- подделка серверной авторизации;
- кража токенов и учётных данных;
- отключение антивируса, Secure Boot или проверки подписи драйверов;
- автоматическое создание исключений безопасности.

Интеграция, пересекающая эту границу, не добавляется в официальный каталог,
даже если её исходный код опубликован.

## 20. Модель разрешений

До установки пользователь видит запрашиваемые возможности:

```text
Эта интеграция сможет:
✓ скачать файлы с github.com/owner/repository
✓ запускать verified-patcher.exe
✓ изменить AppName/config.json
✓ сохранить резервную копию
✓ восстановить исходный файл
```

Разрешения выдаются конкретной версии интеграции. Если обновление добавляет
новое разрешение, требуется повторное подтверждение.

Журнал и UI используют одинаковые типы разрешений, чтобы отображаемое обещание
совпадало с фактическими действиями runtime.

## 21. Логи и приватность

Общий структурированный лог содержит:

- интеграцию и версию;
- операцию и шаг;
- результат precondition и postcondition;
- код завершения процесса;
- хеш плана;
- список созданных и восстановленных ресурсов;
- причину ошибки;
- результат rollback.

Не записываются:

- пароли;
- cookies;
- access/refresh tokens;
- содержимое пользовательского трафика;
- персональные пути без необходимости;
- полный конфигурационный файл, если в нём могут быть секреты.

Диагностический экспорт должен предварительно обезличиваться и показываться
пользователю до отправки.

## 22. Тестирование

### Общие contract tests

Каждая интеграция автоматически проходит один набор тестов:

- манифест соответствует схеме;
- все пути остаются внутри package/runtime root;
- declared capabilities имеют реализацию;
- `Install` идемпотентен;
- `Apply` идемпотентен;
- `Verify` проверяет ожидаемый эффект;
- `Revert` возвращает baseline;
- `Uninstall` сначала выполняет `Revert`;
- повторный `Revert` безопасен;
- отмена операции вызывает rollback;
- сбой после каждого мутирующего шага восстанавливается;
- чужие процессы, службы, файлы и значения реестра не изменяются;
- повреждённый файл или неверный хеш блокирует запуск;
- неизвестное разрешение блокирует пакет.

### Тесты декларативного runtime

- path traversal и reparse points;
- архивные бомбы и лимиты размера;
- запрещённые URL и редиректы;
- подмена хеша;
- неверная Authenticode-подпись;
- небезопасные аргументы CLI;
- конфликт ресурсов;
- атомарность journal;
- rollback в обратном порядке.

### Windows VM

Для системных интеграций обязательны сценарии на чистых Windows 10/11 x64:

- Defender включён;
- Secure Boot включён;
- обычный пользователь и UAC;
- перезагрузка во время активной интеграции;
- сон и смена сети;
- обновление стороннего приложения;
- уже существующий одноимённый процесс или служба;
- прерывание NetBypass на каждом этапе;
- полное удаление и повторная установка.

## 23. Процесс добавления интеграции

1. Создать issue с описанием проблемы и upstream-проекта.
2. Выполнить аудит репозитория и лицензии.
3. Определить минимальные разрешения.
4. Выбрать декларативный рецепт или кодовый адаптер.
5. Создать `integrations/<id>` по стандартной структуре.
6. Описать совместимость и targets.
7. Реализовать `Install`, `Apply`, `Verify`, `Revert`, `Uninstall`.
8. Добавить лицензии, notices, хеши и источник.
9. Пройти contract tests.
10. Пройти ручную проверку в Windows VM.
11. Подписать пакет.
12. Добавить версию в preview-каталог.
13. После тестирования перевести в stable.

Для типовой декларативной интеграции основные проекты и общий UI на этих шагах
не изменяются.

## 24. Миграция текущего проекта

### Этап 1. Отделить платформу от UI

- создать `NetBypass.Integration.Abstractions`;
- создать `NetBypass.Integration.Runtime`;
- ввести `IntegrationCoordinator`;
- ввести общий `ResourceJournal`;
- заменить engine-specific поля `MainViewModel` коллекцией
  `IntegrationItemViewModel`;
- сохранить текущий пользовательский сценарий без функциональных изменений.

### Этап 2. Первая эталонная интеграция

- вынести GoodbyeDPI в отдельный пакет;
- добавить проверку SHA-256 и безопасную распаковку;
- перевести WinDivert cleanup на ownership-модель;
- пройти общий contract test lifecycle.

GoodbyeDPI удобен как первый пример, потому что его жизненный цикл проще.

### Этап 3. Сложный кодовый адаптер

- вынести zapret2 в отдельный пакет;
- перенести каталог стратегий внутрь пакета;
- сохранить автоматический подбор;
- удалить знания о zapret2 из `MainViewModel`;
- проверить переключение двух конфликтующих сетевых интеграций через
  координатор.

### Этап 4. Декларативная системная интеграция

- реализовать `windows-region`;
- сохранять исходный GeoID;
- применять выбранный регион только по явному действию;
- показывать влияние на Store и приложения;
- проверять и восстанавливать исходное состояние.

Эта интеграция доказывает, что платформа работает не только с сетевыми
движками.

### Этап 5. Первый app-patcher

- выбрать безопасный популярный open-source-проект;
- зафиксировать поддерживаемую версию приложения;
- реализовать обнаружение, backup, apply, verify и revert;
- проверить автоматическое отображение на странице целевого приложения.

### Этап 6. Удалённый каталог

- ввести подписанный индекс;
- добавить preview/stable-каналы;
- реализовать side-by-side update и rollback;
- добавить отзыв скомпрометированных версий.

## 25. Критерии готовности платформы

Платформа считается готовой к массовому добавлению интеграций, когда доказано:

- новую декларативную интеграцию можно добавить без изменения App и Core;
- UI автоматически строит карточку и действия из манифеста;
- ни одна интеграция не обходит координатор;
- каждая мутация предварительно записывается в journal;
- после сбоя выполняется восстановление;
- чужие ресурсы не удаляются;
- интеграция показывает upstream, автора, лицензию и версию;
- неподписанный или изменённый пакет не загружается;
- обновление может быть откачено;
- `Revert` и `Uninstall` проходят contract tests;
- GoodbyeDPI и zapret2 работают через тот же публичный контракт, который будет
  использоваться будущими интеграциями.

До выполнения этих условий добавление десятков патчеров следует отложить:
иначе технический долг будет умножаться вместе с каждой интеграцией.

## 26. Итоговая продуктовая модель

```text
Пользователь выбирает проблему
        ↓
NetBypass находит подходящие интеграции
        ↓
Показывает источник, риск и требуемые изменения
        ↓
Строит воспроизводимый план
        ↓
Применяет через единый coordinator и journal
        ↓
Проверяет фактический результат
        ↓
В любой момент возвращает исходное состояние
```

В этой модели NetBypass не конкурирует с отдельными Anti-DPI-проектами и
патчерами. Он становится единым менеджером проверенных решений: упрощает их
установку, скрывает необязательную техническую сложность, честно указывает
авторство и обеспечивает то, чего обычно не хватает отдельным утилитам — общий
UX, совместимость, проверку результата и безопасный откат.
