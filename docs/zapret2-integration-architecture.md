# Интеграция zapret2 в NetBypass

Статус: архитектурный проект, реализация ещё не начата.  
Дата исследования: 29 июля 2026 года.

## 1. Цель

Добавить zapret2 как самостоятельный внешний Anti-DPI-движок для Windows,
которым NetBypass полностью управляет: устанавливает проверенную версию,
создаёт ограниченную выбранными сервисами конфигурацию, запускает, проверяет,
останавливает и удаляет все созданные им системные ресурсы.

Интеграция не должна превращаться в запуск произвольного `.cmd` из скачанного
архива. NetBypass должен владеть конфигурацией и lifecycle движка, а upstream-
архив использовать только как источник неизменяемых бинарников, Lua-библиотек,
WinDivert и лицензионных файлов.

## 2. Подтверждённые свойства zapret2

На Windows главным процессом является `winws2.exe`. Он перехватывает пакеты
через WinDivert, классифицирует соединения и payload, выбирает первый
подходящий профиль и вызывает последовательность Lua-функций, меняющих или
дополняющих пакеты.

Важные для NetBypass свойства:

- `winws2` требует права администратора для инициализации WinDivert;
- после инициализации WinDivert процесс понижает mandatory level и удаляет из
  токена почти все привилегии;
- TCP, UDP и дополнительные raw-фильтры WinDivert задаются отдельно;
- точный фильтр важен для производительности: перехват целого порта направляет
  через user mode весь подходящий трафик;
- стратегии состоят из упорядоченных профилей; выигрывает первый совпавший;
- Lua-файлы являются исполняемой частью стратегии и должны соответствовать
  версии `winws2`;
- длинную конфигурацию можно передать как единственный аргумент
  `@config_file`; остальные аргументы при этом игнорируются;
- `--dry-run` проверяет параметры и доступность файлов, но не синтаксис Lua;
- `--intercept=0` позволяет инициализировать Lua без включения перехвата;
- Windows-сборка умеет работать как служба и обрабатывает команды stop и
  shutdown штатным завершением packet loop;
- хостлисты перечитываются при изменении файла; SIGHUP также инициирует
  перечитывание, но Windows-сигналы работают только внутри одной среды Cygwin;
- `winws2.exe`, запущенному отдельно, нужна `cygwin1.dll` рядом с ним;
- WinDivert может конфликтовать с антивирусами, фаерволами, VPN и другими
  kernel-фильтрами;
- Windows ARM64 требует неподписанный ARM64-драйвер и test-signing mode, а сам
  `winws2` работает через x64-эмуляцию;
- Windows Internet Connection Sharing/NAT не является поддержанным сценарием
  перехвата проходящего трафика.

На дату исследования последним релизом официального репозитория отображался
`v0.9.5.2`. Эта версия зафиксирована только как результат исследования, а не
как автоматическое правило «всегда скачивать latest».

## 3. Продуктовые решения

### 3.1. zapret2 — отдельный адаптер

Нельзя расширять `GoodbyeDpiRuntimeService` условными ветками. Нужны общий
контракт внешнего движка и отдельные реализации:

```text
ExternalEngineCoordinator
├── GoodbyeDpiAdapter
└── Zapret2Adapter
    ├── Zapret2PackageService
    ├── Zapret2CompatibilityService
    ├── Zapret2ConfigBuilder
    ├── Zapret2WindowsService
    ├── Zapret2StrategyOptimizer
    └── EngineResourceJournal
```

UI обращается только к `ExternalEngineCoordinator` и не знает о `sc.exe`,
WinDivert, Lua или расположении runtime-файлов.

### 3.2. Один активный внешний движок

В первой версии одновременно работает только один управляемый Anti-DPI-
движок. Перед запуском zapret2 координатор штатно останавливает GoodbyeDPI и
проверяет очистку. Перед запуском GoodbyeDPI делает обратное.

Несколько обработчиков WinDivert технически возможны, но пересекающиеся
фильтры делают порядок обработки и итоговую стратегию непредсказуемыми.
Совместная работа движков может появиться позже только после отдельного
исследования.

### 3.3. Один процесс winws2 с несколькими профилями

Для всех выбранных сервисов строится одна конфигурация `winws2`. В ней
сервисные стратегии объединяются в упорядоченный список профилей. Это даёт:

- один WinDivert handler и один lifecycle;
- единый контроль конфликтов фильтров;
- предсказуемый порядок `--new`-профилей;
- один журнал ресурсов и одну операцию очистки;
- меньшую нагрузку, чем несколько процессов с пересекающимися фильтрами.

Конфигуратор обязан проверять пересечения и порядок профилей. Универсальный
профиль без hostlist всегда располагается после узких сервисных профилей.

### 3.4. Служба запускается вручную, не автоматически

Рекомендуемый runtime для первой версии — штатная Windows-служба `winws2` со
стартом `demand`.

Причины:

- upstream реализует корректную обработку `SERVICE_CONTROL_STOP`;
- NetBypass может надёжно дождаться состояний RUNNING и STOPPED;
- закрытие UI не останавливает обход;
- фоновый запуск NetBypass может восстановить службу и завершиться;
- аварийный cleanup не зависит от сохранённого объекта `Process`.

Центральная задача автозапуска NetBypass остаётся единственной точкой
восстановления. Сама служба zapret2 не получает `start=auto`.

Upstream использует имя `winws2` в service dispatcher. Перед реализацией нужен
короткий Windows-spike: подтвердить работу под собственным именем
`NetBypassZapret2`. Если собственное имя не поддерживается, используется
`winws2`, но только после проверки владельца существующей службы. Чужая служба
никогда не перенастраивается и не удаляется — NetBypass показывает конфликт.

## 4. Поддерживаемая платформа MVP

Первая поставка:

- Windows 10/11 x64;
- запущенный от администратора NetBypass;
- локальный клиентский трафик;
- IPv4 и IPv6, если профиль явно это поддерживает;
- без Internet Connection Sharing, router/NAT-сценария и виртуальной машины с
  NAT-сетью;
- без Windows ARM64 и без автоматического включения test-signing;
- без Windows 7 и 32-битной Windows.

NetBypass никогда автоматически не отключает Secure Boot, антивирус, фаервол,
защиту драйверов или другие средства безопасности. Он показывает точную
причину несовместимости и оставляет решение пользователю.

## 5. Установка и обновление

### 5.1. Источник пакета

Предпочтение отдаётся архиву фиксированного релиза официального репозитория
`bol-van/zapret2`. Если он не содержит полного автономного Windows x64 runtime,
допускается официальный `bol-van/zapret-win-bundle`, но только архив конкретного
commit, а не изменяемая ветка `master`.

До реализации downloader нужен отдельный package-audit выбранного архива:

1. проверить состав архива;
2. определить обязательные `winws2.exe`, `cygwin1.dll`, WinDivert DLL/SYS,
   upstream Lua и blob-файлы;
3. записать SHA-256 архива и критических файлов;
4. сохранить точные LICENSE/NOTICE всех компонентов;
5. проверить архитектуру PE-файлов;
6. подтвердить запуск `--version`, `--dry-run` и `--intercept=0` в чистой VM.

### 5.2. Версионированное размещение

```text
%LOCALAPPDATA%\NetBypass\Engines\zapret2\
├── package-manifest.json
└── 0.9.5.2\
    ├── winws2.exe
    ├── cygwin1.dll
    ├── WinDivert.dll
    ├── WinDivert64.sys
    ├── lua\
    ├── files\
    └── licenses\

%LOCALAPPDATA%\NetBypass\Runtime\zapret2\
├── active.conf
├── candidate.conf
├── hostlists\
├── filters\
├── logs\
└── resource-journal.json
```

Каталог версии после установки неизменяемый. Все создаваемые NetBypass файлы
находятся в `Runtime`. Обновление устанавливается side-by-side, проверяется и
только после успешного запуска становится `current`. Предыдущая версия
сохраняется для отката.

### 5.3. Безопасная распаковка

Installer обязан:

- отклонять абсолютные пути, `..`, reparse points и выход за install root;
- распаковывать во временную директорию;
- сверять размер и SHA-256 до активации;
- атомарно переименовывать проверенный каталог;
- не выполнять `.cmd`, `.ps1` или install-скрипты из архива;
- не скачивать стратегии и Lua с произвольных URL во время запуска.

## 6. Модель профилей NetBypass

Профиль zapret2 хранится в репозитории NetBypass и проходит code review. Это не
готовый `.cmd`, а декларативный каталог:

```json
{
  "schemaVersion": 1,
  "catalogVersion": 1,
  "engine": "zapret2",
  "engineVersion": "0.9.5.2",
  "luaCompatibility": 1,
  "profiles": [
    {
      "id": "https-tcp-conservative",
      "name": "HTTPS · щадящий",
      "priority": 10,
      "risk": "low",
      "protocols": ["tcp-tls"],
      "serviceIds": ["youtube", "discord"],
      "requiredAssets": ["zapret-lib", "zapret-antidpi"],
      "arguments": ["...версионированные аргументы..."]
    }
  ]
}
```

Каталог обязан фиксировать совместимость с конкретной версией движка и Lua.
Каталог от другой версии не запускается.

`Zapret2ConfigBuilder` разрешает только известные placeholders и проверенные
пути. Он отклоняет:

- NUL, CR/LF внутри аргумента и вложенный `@config`;
- пути вне package/runtime roots;
- `--daemon`, `--pidfile`, `--debug`, `--writable` и другие параметры,
  которыми владеет runtime;
- неизвестные Lua-файлы и blob-файлы;
- конфигурацию больше допустимого upstream размера;
- несовместимые или неправильно упорядоченные профили.

Пользовательский Lua и свободное текстовое поле аргументов не входят в MVP.
Позже их можно добавить только как отдельный «Экспертный режим» с явным
предупреждением и без автоматического доверия.

## 7. Построение active.conf

Конфигурация строится детерминированно:

1. контролируемые runtime-параметры;
2. минимальный WinDivert capture filter;
3. upstream Lua initializers;
4. blob-файлы;
5. узкие профили выбранных сервисов;
6. универсальный fallback-профиль, если он нужен;
7. комментарий с идентификатором каталога и хешем плана.

Домены выбранных сервисов записываются в отдельные hostlist-файлы. Они не
встраиваются длинной строкой в конфигурацию. При снятии сервиса его домены
исчезают из hostlist, после чего применяется новая конфигурация.

В первой версии изменение набора сервисов выполняется безопасным restart:

```text
build candidate → validate → stop service → atomically replace active.conf
→ start service → verify → commit journal
```

Горячая перечитка hostlist через Cygwin signal остаётся оптимизацией на будущее:
она не должна быть единственным механизмом управления.

## 8. Lifecycle адаптера

### 8.1. Состояния

```text
NotInstalled
  → Installed
  → Preparing
  → Starting
  → RunningUnverified
  → RunningVerified
  → Stopping
  → Stopped
  → Cleaning
  → Clean

Любое промежуточное состояние → Faulted → Recovering → Clean
```

### 8.2. Preflight

Перед первой системной мутацией:

1. проверить OS/архитектуру и права;
2. проверить package manifest и хеши;
3. проверить отсутствие чужих `winws2`, GoodbyeDPI и конфликтующей службы;
4. построить `candidate.conf` и hostlist-файлы;
5. запустить конфиг с `--dry-run`;
6. запустить отдельный preflight с `--intercept=0`, чтобы инициализировать Lua;
7. убедиться, что команда завершилась с кодом 0;
8. зафиксировать baseline системных ресурсов в journal.

`--dry-run` и `--intercept=0` являются двумя разными проверками: первая ловит
ошибки аргументов и путей, вторая — ошибки загрузки/инициализации Lua.

### 8.3. Start

1. получить глобальный lock `Global\NetBypass.ExternalEngine`;
2. остановить другой управляемый движок;
3. записать write-ahead journal со статусом `Preparing`;
4. создать или обновить только принадлежащую NetBypass службу;
5. запустить службу;
6. дождаться RUNNING с ограниченным timeout;
7. убедиться, что image path и PID соответствуют NetBypass package;
8. выполнить сетевую post-check;
9. сохранить `RunningVerified` и активный план.

Сам факт RUNNING не означает, что обход работает. Успех устанавливается только
после сетевой проверки выбранных сервисов.

### 8.4. Stop и cleanup

1. отправить `sc stop` и дождаться STOPPED;
2. при timeout записать проблему и только затем завершить принадлежащий
   NetBypass PID;
3. удалить созданную NetBypass службу;
4. сравнить WinDivert services/drivers с baseline;
5. удалить только ресурсы, появившиеся в нашей транзакции;
6. удалить active runtime-файлы, оставив диагностический журнал;
7. проверить отсутствие принадлежащих NetBypass процессов и служб;
8. записать `Clean`.

Нельзя, как сейчас делает ранний GoodbyeDPI runtime, безусловно удалять все
известные службы WinDivert. Перед zapret2 требуется общий ownership-aware
cleanup: чужой или существовавший до запуска драйвер не трогаем.

## 9. Resource Journal и восстановление

Журнал записывается до каждой системной мутации и содержит:

```json
{
  "schemaVersion": 1,
  "operationId": "...",
  "engine": "zapret2",
  "engineVersion": "0.9.5.2",
  "state": "RunningVerified",
  "service": {
    "name": "NetBypassZapret2",
    "createdByNetBypass": true,
    "imagePath": "...",
    "processId": 1234
  },
  "configSha256": "...",
  "resourcesBefore": ["..."],
  "resourcesCreated": ["..."],
  "updatedAt": "2026-07-29T20:00:00Z"
}
```

При старте приложения незавершённый журнал имеет приоритет над обычным UI:

- проверить фактические process/service/image path;
- если сохранённый выбранный план всё ещё актуален — завершить восстановление
  и повторно проверить сеть;
- иначе выполнить cleanup в обратном порядке;
- никогда не «усыновлять» ресурс только по совпадению имени.

Запись выполняется через временный файл и атомарную замену. Journal хранит
канонические абсолютные пути и хеши, а не только PID.

## 10. Поиск рабочей стратегии

Используется существующая идея `GoodbyeDpiStrategyOptimizer`, но общий контракт
выносится из GoodbyeDPI-специфичного кода.

Алгоритм:

1. остановить все управляемые Anti-DPI-движки;
2. выполнить baseline-проверку напрямую;
3. если сервис уже доступен — не включать zapret2 без необходимости;
4. сначала проверить сохранённый план с совпадающими версиями движка, каталога
   и выбранным набором сервисов;
5. затем проверять curated-профили от low risk к high risk;
6. после старта каждого кандидата дождаться стабилизации;
7. выполнить мультипроверку всех обязательных сервисов;
8. проверить контрольный незаблокированный домен, чтобы стратегия не ломала
   обычный HTTPS;
9. после неудачного кандидата полностью остановить его перед следующим;
10. выбрать минимально рискованный рабочий профиль, а задержку использовать
    только как дополнительный score;
11. сохранить выбранный составной план и повторно проверить его после
    финального запуска.

Успешный TCP/TLS тест проверяет только TCP-часть. Для профилей QUIC, Discord
voice/STUN и других UDP-протоколов нужны отдельные protocol-aware probes.
До появления таких probes профиль не может помечаться полностью проверенным.

`blockcheck2` полезен как исследовательский инструмент, но не входит в первый
автоматический pipeline: upstream требует остановить другие средства обхода,
сканирование может быть долгим, а найденный результат ещё нужно преобразовать
в безопасный curated-профиль. Позже его можно добавить в экспертную
диагностику с отдельным согласием пользователя.

## 11. Логи и наблюдаемость

NetBypass ведёт собственный структурированный журнал:

- версия package и catalog;
- config hash без полного раскрытия пользовательских путей;
- действия SCM и их exit codes;
- длительность старта/остановки;
- результаты probes по сервисам;
- созданные и удалённые ресурсы;
- причина отказа и cleanup status.

Постоянный upstream `--debug` по умолчанию выключен: документация предупреждает,
что файл ничем не ограничивается. Диагностический режим включает его только на
ограниченный сеанс, предварительно ротирует файл и выключает после
воспроизведения проблемы.

Логи не должны содержать полный пользовательский трафик, payload, токены,
cookies или содержимое TLS-сессий.

## 12. Изменения общей архитектуры NetBypass

Перед Zapret2 нужны следующие общие контракты:

```csharp
public interface IExternalEngineAdapter
{
    string Id { get; }
    Task<EngineAvailability> CheckAvailabilityAsync(CancellationToken ct);
    Task<EngineCompatibility> CheckCompatibilityAsync(CancellationToken ct);
    Task<EngineInstallResult> InstallAsync(CancellationToken ct);
    Task<EngineStartResult> StartAsync(EngineStartPlan plan, CancellationToken ct);
    Task<EngineStatus> GetStatusAsync(CancellationToken ct);
    Task<EngineStopResult> StopAsync(CancellationToken ct);
    Task<EngineCleanupResult> RecoverAndCleanupAsync(CancellationToken ct);
}
```

Дополнительные сервисы:

- `ExternalEngineCoordinator` — эксклюзивность и переключение движков;
- `EnginePackageManifestService` — версии, хеши и атомарное обновление;
- `EngineResourceJournal` — write-ahead ownership и crash recovery;
- `WindowsServiceManager` — типизированная обёртка над SCM;
- `AntiDpiPlanOptimizer` — общий цикл start/probe/score/rollback;
- `ProtocolProbeRegistry` — TCP/TLS/HTTP, QUIC и специализированные UDP probes.

`ISystemCommandRunner` нужно расширить типизированными результатами и
поддержкой timeout. Проверка процесса не должна возвращать `true` только потому,
что чтение `MainModule` запрещено: для системных ресурсов требуется доказанное
совпадение image path или явное состояние `Unknown`.

## 13. UI

Карточка zapret2 показывает:

- не установлен / установлен / запущен / проверен / требует очистки;
- точную версию;
- активный составной профиль;
- поддерживаемые выбранные сервисы;
- предупреждение о WinDivert и возможной реакции защитного ПО;
- кнопки «Скачать», «Проверить совместимость», «Включить», «Остановить»,
  «Удалить»;
- журнал последней проверки и cleanup.

При конфликте показывается конкретный ресурс:

```text
Обнаружена чужая служба winws2.
NetBypass не будет изменять или удалять её автоматически.
```

Не должно быть кнопок «отключить антивирус» или автоматического создания
исключений.

## 14. План реализации

### Этап 0. Package и Windows spike

- зафиксировать upstream release/commit и SHA-256;
- проаудировать содержимое Windows-пакета и лицензии;
- проверить Windows 10/11 x64 в чистой VM;
- проверить custom service name, stop/shutdown и driver cleanup;
- проверить `@config`, `--dry-run`, `--intercept=0` и максимальный размер config.

Критерий: воспроизводимый install manifest и документированный SCM lifecycle.

### Этап 1. Общая инфраструктура движков

- `IExternalEngineAdapter` и coordinator;
- ownership-aware resource journal;
- `WindowsServiceManager`;
- безопасный package installer;
- перевести cleanup GoodbyeDPI на ownership-модель.

Критерий: fake adapter проходит start/stop/crash-recovery тесты и не трогает
чужие процессы/службы.

### Этап 2. Zapret2 runtime без автоподбора

- install/uninstall;
- compatibility preflight;
- config builder и hostlists;
- service start/stop/status;
- один консервативный TCP/TLS curated-профиль;
- post-start TCP/TLS/HTTP проверка;
- UI карточки и cleanup report.

Критерий: ручное включение и выключение в VM не оставляет процесса, службы,
драйвера или runtime-конфига.

### Этап 3. Автоматический подбор

- общий optimizer;
- набор проверенных TCP-профилей;
- сохранение рабочего плана;
- rollback каждого неудачного кандидата;
- восстановление через существующий background startup NetBypass.

Критерий: сохранённый профиль сначала перепроверяется, нерабочий автоматически
заменяется, а failed attempt не оставляет активный WinDivert handler.

### Этап 4. UDP/QUIC и расширенные сервисы

- QUIC probe;
- Discord voice/STUN probe;
- узкие `--wf-raw-part` фильтры;
- CPU/load guardrails;
- расширение каталога сервисов.

Критерий: UDP-профиль получает статус Verified только по protocol-aware probe.

### Этап 5. Обновления и экспертная диагностика

- side-by-side update и rollback;
- ограниченный диагностический debug-session;
- опциональный blockcheck2 workflow;
- экспорт обезличенного диагностического отчёта.

## 15. Обязательные тесты

Unit:

- path traversal и symlink/reparse-point защита;
- hash mismatch и повреждённый archive;
- config rendering, порядок профилей и запрещённые аргументы;
- journal transitions и атомарная запись;
- ownership: чужая служба/процесс/драйвер никогда не удаляются;
- rollback после ошибки на каждом шаге;
- сохранённый профиль инвалидируется версией engine/catalog/Lua.

Integration с fake SCM/runner:

- install → preflight → start → verify → stop → clean;
- timeout START_PENDING/STOP_PENDING;
- процесс завершился сразу;
- UAC отменён;
- stale PID принадлежит другому executable;
- падение приложения после каждой write-ahead записи;
- переключение GoodbyeDPI ↔ zapret2.

Windows VM:

- Windows 10 x64 и Windows 11 x64;
- Defender включён;
- Secure Boot включён;
- IPv4/IPv6;
- сон/пробуждение, смена сети, выход/вход пользователя;
- перезагрузка при активном плане;
- конфликт с уже установленным `winws2`;
- VPN/фаервол: корректное сообщение и отсутствие destructive cleanup;
- удаление движка после аварийного завершения NetBypass.

## 16. Go/no-go критерии первой поставки

Интеграция не выпускается, пока не доказано:

- package воспроизводим и проверяется по SHA-256;
- лицензии и notices включены;
- Lua и binary жёстко совместимы по версии;
- чужие системные ресурсы не изменяются;
- stop действительно завершает обработку пакетов;
- после cleanup нет принадлежащих NetBypass process/service/driver;
- обычный контрольный HTTPS не ломается;
- профиль считается рабочим только после post-check;
- отказ, отмена UAC и crash приводят к восстановимому состоянию;
- приложение не предлагает ослаблять системную безопасность автоматически.
